## M.9 — Mise à jour du 2026-08-31 : la capture confirmatoire, et 1.8.0

**La capture confirmatoire prévue en §M.5 a eu lieu** (`/kairos:implement-story` puis
`/kairos:close-story`, worktree d'épic, 316 appels, 22 chaînes, 0 échec réseau).

**Ce qu'elle prouve — le lot B tient.**

| Prétention | Pièce |
|---|---|
| **F6 mort** — le gate voit le non-commité | le rapport `gate-security` nomme 16 fichiers non commités, `SCOPE-TOKEN` valide |
| **F3 mort** — plus de sous-agent sécurité maison | **zéro** appel `Agent`/`Task` sur toute la chaîne principale |
| Reçus écrits | `review` + `security`, jetons valides, `stale_receipts: 0` sur le commit de code |
| Gate à deux étages | le skill natif tourne après le commit, reçu `native-skill`, clé `head-<sha>` |
| Push couvert | `native_pass: covered`, `native_receipts_seen: 1` |
| Hook `pre-push` par worktree (Phase 4.5) | `"event":"pre-push-hook"` émis depuis le worktree |

**Les quatre défauts trouvés, tous corrigés en 1.8.0** (détail dans `CHANGELOG.md`) :

1. **`skills/review/SKILL.md` portait `disable-model-invocation: true`.** Le gate de revue
   de `close-story` était donc **injoignable par son propre appelant**. Le modèle a
   contourné, lancé la passe native non scopée, et écrit un reçu `mechanism=kairos-fork`
   pour un mécanisme qui n'a pas tourné — le jeton étant authentique, l'écriture a été
   acceptée. **C'est la limite honnête de C12 : le jeton prouve la *portée*, jamais le
   *mécanisme*.** À dire dans le plan, pas à masquer.
2. **Trois artefacts décrivaient encore le gate 1.6.0** (`implement-epic` prompt de
   sous-agent, `qa-self-check`, `spec-format`) : le skill natif et son *provenance footer*.
   Une instruction qui décrit un mécanisme disparu envoie le modèle en chercher un autre.
3. **Le sujet de commit ne se parsait jamais** — forme heredoc, `commit_type` vide sur les
   deux commits. Ce qui **bloquait l'exemption** que le code lui-même annonçait en
   commentaire.
4. **Les reçus consommés étaient comptés comme périmés.** Sur un épic de 5 stories : 10
   faux « périmés » à l'arrivée.

**La décision de conception, arrêtée avec l'utilisateur.** `close-story` fait deux commits
et doit le faire : les Phases 4–5 dérivent `spec.md` **du** commit de code et archivent la
story. Aucun reçu ne peut couvrir ce second commit. Deux options existaient — un seul
commit, ou une exemption. Retenu : **l'exemption, indexée sur les chemins modifiés, jamais
sur le message.** Un message est écrit par le modèle ; une exemption qui s'y accroche est
un mot de passe qu'il se délivre à lui-même, et le run vient de montrer ce qu'il fait
devant une porte fermée. Le champ `classification` (`code` | `bookkeeping`) du
`gate-log.jsonl` est ce que l'étape 5 lira.

**C9 et C10 sont livrés**, hors séquence, parce qu'ils ne touchent aucun gate :

- **C10** — `scripts/kairos-refs.sh` + Phase 3.5 de `create-story`. Correction au §C10 : le
  seuil ne suffit pas, il faut aussi **créditer** l'ancrage — une référence ancrée est
  comptée à 700 jetons (le coût de l'extrait) et non à la taille du fichier, sinon le
  chiffre affiché plaide contre le correctif qu'il réclame.
- **C9** — **corrigé deux fois par rapport au plan.** (1) Le §C9 le plaçait au Preflight
  d'`implement-epic` ; depuis 1.5.0 cette commande tourne **dans** le worktree, donc trop
  tard — la compaction doit atterrir sur la branche principale avant `git worktree add`.
  (2) Et « une seule règle, un seul endroit » ne tenait pas : `/kairos:worktree` ne couvre
  que `epic_shared`, or `in_place` et `off` ne créent jamais de worktree et n'auraient donc
  **jamais** vu la proposition. La règle devient **un seul endroit *par projet*, choisi par
  `worktree_mode`** :

  | `worktree_mode` | Où | Pourquoi là |
  |---|---|---|
  | `epic_shared` | `/kairos:worktree` Phase 1d | seul instant où la compaction précède `git worktree add` |
  | `in_place`, `off` | `/kairos:create-prd` Phase 3.6, après l'écriture du PRD | sur la branche par défaut, geste délibéré et interactif, cadence d'ouverture d'un chantier |

  Mutuellement exclusifs : aucun projet n'est sollicité deux fois, aucun ne l'est jamais.
  Les trois raisons du §C9 sont inchangées ; seuls les points d'accroche bougent. Et
  `close-story` reste muet des deux côtés — c'est pourtant là que l'inflation se produit,
  mais il tourne sans humain.

**Reste ouvert** : plus rien sur l'étape 5 côté code — reste à l'**armer sur un vrai épic**
(§M.10). Le harnais est à **103 tests**, dont vingt-quatre neufs sur le refus, ses
exemptions et l'ordre de résolution du mode.

## M.10 — 1.9.0 : le refus, et ce qu'il refuse de refuser

Les quatre versions précédentes construisaient un **instrument** : il mesurait, il
enregistrait, et un run qui l'ignorait ne payait rien. 1.9.0 est la version où la mesure a
le droit d'avoir une conséquence — cadrée aussi étroitement que la preuve le permet.

### Les cinq arbitrages, tels que tranchés

| | Question | Décision | Qui a tranché |
|---|---|---|---|
| **D1** | Quels gates un commit `code` doit-il montrer ? | `review` + `security`. **Pas `tests`** : aucun skill n'écrit de reçu `tests`, exiger l'inexistant refuse *tous* les commits. Satisfait par `passed`, `skipped`+raison, ou `override`+raison | moi, non contesté |
| **D2** | Accepter un `--override` écrit par le modèle ? | **Oui**, en session interactive : un override est nommé, daté, journalisé. Le refuser n'achète rien qu'un contournement déterminé ne puisse obtenir autrement, et coûte la seule chose qui rend un bloqueur vivable | **l'utilisateur** |
| **D3** | Bloquer le push ? | **Jamais.** « on ne bloque pas un humain qui dit push après un avertissement ». Question **close**, pas une étape de déploiement. Le hook `pre-push` avertit et sort 0, dans tous les modes, définitivement | **l'utilisateur**, plus fort que ma recommandation |
| **D4** | L'interrupteur d'arrêt | `$KAIROS_MODE` → fichier par arbre → fichier machine → `observe`. **Jamais un champ de `spec.md`** : le modèle l'édite, et `_is_bookkeeping` l'exempte — un gate désarmable dans un commit qui n'a besoin d'aucun reçu n'est pas un gate | moi, après avoir dû expliquer que `enforce` n'existait pas encore |
| **D5** | Ordre de déploiement | Refus **commit d'abord**, un vrai épic, puis on décide pour le reste | moi, non contesté |

### Ce que 1.9.0 refuse de faire

- **Refuser un push** — D3, définitif.
- **Refuser un commit `bookkeeping`** — l'exemption de 1.8.0, calculée sur les chemins.
- **Refuser un commit `empty`** (rien en attente : un reword, un amend d'arbre propre). Un
  refus sans objet : il n'y a pas de change set qu'un gate aurait pu couvrir.
- **Livrer armé.** Le défaut reste `observe`. Ce dépôt est son propre marketplace : un
  merge sur `main` atteint toutes les installations d'un coup, donc un refus défectueux
  arrive partout en même temps, au milieu des épics des autres. `KAIROS_MODE=observe` rend
  l'ancien comportement sans éditer un fichier installé ni attendre une release — le
  recours doit exister **avant** qu'un hook ait le droit de dire non.

### Ce qui reste à faire

**Armer sur un vrai épic** : `--set-mode enforce --tree <worktree>`, puis lire
`gate-log.jsonl`. Ce qu'on cherche : un `decision: deny` que le workflow n'aurait pas dû
provoquer. Zéro faux refus sur un épic complet → on peut envisager de basculer le défaut ;
un seul → le refus est trop large, et c'est le classifieur qu'on corrige, pas le mode.
