## M.4 — Chantiers neufs et corrections aux chantiers existants

### C12 — Le reçu prouve, il n'atteste plus *(neuf — remplace la moitié « producteur » de C7)*

**Vise** F8. Le producteur d'aujourd'hui écrit ce que le modèle lui dit d'écrire.

**Mécanisme — le jeton de portée.** `kairos-diff.sh` fait trois choses en un geste :

1. calcule le diff de portée et son condensé ;
2. tire un **nonce** et l'écrit dans `$XDG_STATE_HOME/kairos/<arbre>/pending/<digest>.token` ;
3. **imprime le nonce en tête du diff injecté** : `SCOPE-TOKEN: <nonce>`.

Le gate doit alors **rendre le nonce** dans son rapport, et `kairos-gate-receipt.sh --write`
**refuse d'écrire sans nonce correspondant**. Un gate qui n'a pas consommé le diff produit
par Kairos ne peut pas produire de reçu.

Ce que ça attrape et ce que ça n'attrape pas — à dire franchement : **ça n'est pas
infalsifiable.** Un modèle déterminé peut recopier le nonce sans lire le diff. Ça élimine
le cas *mesuré*, qui est l'accident : un gate qui n'a **jamais vu** d'artefact Kairos, et
un reçu vert quand même. On passe de « le modèle affirme » à « le modèle prouve qu'il a
tenu l'artefact ». C'est un cran, pas une preuve cryptographique, et le plan ne doit pas
prétendre autre chose.

**Champs ajoutés au reçu :**

```json
{ "gate": "security",
  "result": "passed",
  "mechanism": "kairos-fork | native-skill | override",
  "scope_cmd": "git -C <work> diff --staged -- frontend",
  "scope_token": "<nonce>",
  "reason": "<obligatoire si mechanism=override>" }
```

`mechanism` est ce qui rend l'étape 5 possible : le mode refus pourra exiger *tel*
mécanisme, pas seulement *un* reçu. Et une substitution, si elle a lieu, devient
`passed(kairos-fork)` — **visible, datée, auditable** au lieu de silencieuse.

**Effet de bord utile** : `gate-log.jsonl` gagne la colonne `mechanism`, donc F3 devient
mesurable en continu sur les vrais runs, sans capture télémétrique.

### C13 — Le gate natif se déclenche au push *(neuf — réécrit C3c)*

**Deux hooks, aucun modèle dans la boucle pour la partie contraignante.**

1. **`PostToolUse` sur `Bash`, quand la commande est un `git commit` abouti dans un
   workspace Kairos** → retourne `hookSpecificOutput.additionalContext` : *« commit `<sha>`
   posé sur `<branche>` ; la passe native ne l'a pas encore couvert ; elle est due avant le
   prochain push »*. C'est une **obligation**, pas une exécution.
2. **`PreToolUse` sur `Bash`, quand la commande est un `git push`** → cherche un reçu
   `security` de `mechanism: native-skill` dont le `head` couvre la pointe de branche.
   Absent → **observation** : ligne de journal, on laisse passer. **Refus** (étape 5) :
   `permissionDecision: "deny"` avec le message qui nomme la commande à lancer.

**Le trou connu, et il faut l'écrire** : sous `push_mode: manual`, l'opérateur pousse
depuis **son** terminal — le hook Claude Code ne voit rien. Correctif proposé : un vrai
**hook git `pre-push`** posé dans le worktree par `/kairos:worktree`, qui fait la même
vérification. Ça ne dépend plus de qui pousse ni d'où. **Conditionné à la sonde V9.**

**La transformation**, et rien d'autre :

````diff
- ```
- !pwd
- ```
+ ```!
+ pwd
+ ```
````

**Cinq pièges, tous documentés ou mesurés :**

1. **Seule la clôture ouvrante `` ```! `` tire** (et sa forme en ligne `` !`cmd` ``). Un
   `!cmd` en tête de ligne dans une clôture ordinaire arrive **comme du texte** (F5).
2. **Un code de retour non nul avorte l'invocation entière.** Suffixer `|| true`, ou mieux,
   `|| echo "<valeur de repli lisible>"` comme le fait déjà `worktree`.
3. **Pas de bloc `arguments:` dans un skill qui injecte** (V1). Les formes positionnelles
   `$0`, `$1`, `$ARGUMENTS` sont substituées partout ; déclarer `arguments:` casse la
   substitution **dans** le bloc injecté, et le mode d'échec est une **réponse vide, rc 0,
   rien sur stderr, rien sous `--debug`**.
4. **Ajouter `allowed-tools`** malgré la tolérance observée en 2.1.241 (`worktree` tire
   sans). La doc dit qu'une commande injectée dont la règle de permission ne dit pas
   « allow » **avorte l'invocation** ; ne pas s'appuyer sur une tolérance dont le mode
   d'échec est silencieux.
5. **Convertir un skill à la fois, et fumiger chacun.** Le mode d'échec étant silencieux,
   un `sed` sur les treize fichiers d'un coup peut briquer treize commandes sans un seul
   message d'erreur. Le test de fumée : invoquer le skill et vérifier que la sortie
   contient la **valeur** attendue, pas la commande.

## M.8 — Défaut latent ~~trouvé~~ **confirmé en mesure** dans `scripts/kairos-gate-receipt.sh`

> **Mesuré le 2026-08-30** (sonde hors ligne, cf. §6.2) : ce n'est plus une lecture de code, c'est une sortie observée. Le diagnostic ci-dessous est exact.

`do_verify()` a deux chemins de parsing. Celui de `jq` **préserve les retours à la ligne** ;
celui de `python3` les **remplace par des espaces** puis ne garde que la 2ᵉ ligne.

Or le regex de détection exige un début de ligne ou un séparateur `;&|(` avant `git`. Les
commandes réellement émises par Kairos ont la forme :

```
cd /home/sartois/Documents/Sources/civilia-epic-17-views
git commit -m "…"
```

→ avec `jq` : détecté (le `git` est en début de ligne). **Sans `jq`, sur le chemin
`python3` : jamais détecté**, silencieusement. Le hook se tairait sur toutes les machines
sans `jq`.

À corriger en même temps que C12 (le script est de toute façon rouvert), et à couvrir par
la matrice de détection existante — qui a 11/11 mais ne teste manifestement pas le chemin
de repli.
