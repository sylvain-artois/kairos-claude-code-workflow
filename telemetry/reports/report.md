# Kairos telemetry — pre-analysis for a deep-dive model

Generated by `telemetry/analyze_telemetry.py` from the raw Claude API
capture archives in `telemetry/*.zip`. This file is meant to be read
alongside the CSVs it references — it front-loads what a first pass already found so
a more expensive model (Opus/Fable) can go straight to depth instead of re-deriving
the basics from ~1GB of raw JSON.

**Ask driving this analysis** (from the project owner, in French, paraphrased): Kairos
feels slow, burns a lot of tokens, and there's a specific bug where launching a code
review mid-epic goes sideways — find ways to speed Kairos up, ways to cut token spend,
and pin down what the review bug actually costs in tokens/minutes.

## What's in `reports/`

| File | Grain | Use it for |
|---|---|---|
| `calls.csv` | one row per matched API call (2056 rows) | the raw material — filter/group by archive, tool, effort, turn_index |
| `chains.csv` | one row per conversation chain (472 rows) | which chains (root agent, or a specific subagent spawn) cost the most tokens/time |
| `archive_summary.csv` | one row per archive (4 rows) | headline comparison across configs — the table below is this file, formatted |
| `failed_calls.csv` | requests with no captured response (10 rows) | API calls that errored/never completed |
| `incidents_repeated_skill.csv` | auto-detected same-skill-invoked-≥2×-within-180s clusters (2 rows) | candidate retry/rework loops — the review bug shows up here |

### Archive naming, and what's actually trustworthy in it

Archive names are meaningful but only loosely structured (`kairos-implement-epic-story-119-story-120-story-121-opus-xhigh-thinking`,
`session1_nokairos`, `create-story_prd17`, ...). **Don't parse model/effort/thinking
from the filename** — `calls.csv` has `model` / `effort` / `thinking_type` read
straight out of each request body, which is authoritative; the filename is kept only
as a human label (and `session1_nokairos` is the useful baseline: real coding work,
same project, no Kairos commands, for comparison).

### Column notes worth knowing before you query `calls.csv`

- **`billed_input_tokens`** = `input_tokens_uncached + cache_read_tokens + cache_creation_tokens`.
  This is the real per-call input cost. `cache_read_tokens` is cheap-but-not-free and
  still adds latency (the model still has to attend over it), so don't treat a high
  cache-hit-rate as "this call was free."
- **`gap_before_s`** = time between the *previous* turn's response landing and *this*
  turn's request being sent, within the same conversation chain. This is exact —
  reconstructed via `request.diagnostics.previous_message_id == response.id`, a
  reliable field, not a timing heuristic. It's the best available proxy for "time
  spent outside the model" (tool execution, orchestration, human wait).
- **`latency_s`** = model-side generation time for that specific call. This one *is*
  approximate: the capture format has no explicit request↔response join key (request
  files are named by a local capture uuid, response files by the API's own request
  id), so calls are paired by FIFO-by-timestamp within each archive. This is exact
  under normal sequential operation and only wobbles around a failed/orphaned call.
  `latency_suspect=True` flags the (small) minority of calls where FIFO likely
  mismatched; `archive_summary.csv`'s latency stats already exclude those.
- **`turn_index` / `chain_root`**: position within a conversation chain and an id for
  that chain, both derived from the exact `previous_message_id` link — not
  approximate. A `chain_root` with a small `n_turns` in `chains.csv` and no further
  activity is very likely a subagent (`Task`/`Agent` tool call) that ran its own short
  conversation.

## Finding 1 — where the time actually goes

Splitting `gap_before_s` by what the *previous* turn did (from `calls.csv`, joining
each row to its chain predecessor):

| Archive | gap after a tool-calling turn (mechanical: tool exec, waiting on docker/tests) | gap after a non-tool turn (harness continuation, or a human/approval checkpoint) |
|---|---|---|
| create-story | 190s over 26 gaps (~7s avg) | 224s over 3 gaps |
| epic | 5232s over 420 gaps (~12s avg) | **7928s over just 16 gaps (~495s avg)** |
| wave | 6642s over 302 gaps (~22s avg) | **8392s over just 10 gaps (~839s avg)** |
| baseline | 2562s over 137 gaps (~19s avg) | 13508s over 21 gaps |

Two very different things are hiding in "the workflow is slow":

- **The many small tool-exec gaps** (~7-22s average) are just normal tool round trips
  and aren't where the time is concentrated.
- **A handful of huge non-tool-turn gaps dominate total wall time** in both Kairos
  archives (7928s / 8392s — well over 2 hours combined, out of ~3.5h runs each). These
  follow a turn that ended with `end_turn` and no tool call (see `calls.csv`,
  filter `gap_before_s > 300` and inspect the preceding row's `stop_reason`). Some are
  plausibly genuine checkpoints — Kairos's own contract makes `push` user-driven
  ("prints the git push line and waits for pushed/skip"), which is exactly the shape
  of a long pause with no tool call before it. Others may be idle re-prompts. **This
  data can't fully tell the two apart** — that needs reading the actual text content
  around each specific large gap in the source zip (mtime windows are in `calls.csv`).
  This is the single highest-value place left to dig for the "why is it slow" question.
- The single largest *mechanical* stalls (`kairos-implement-wave...`, 1674s / 864s /
  602s, all following a `Bash` turn) line up with the review-diff detours described in
  Finding 3, and separately with what look like slow test/build commands — worth
  cross-referencing `tool_names` on the preceding row for each one.
- `Bash` dominates tool usage **in every archive, including the no-Kairos baseline**
  (78.8%-97.6%). This is not a Kairos-specific pattern — it's how this agent operates
  in this environment generally (ad-hoc `grep`/`sed`/`git` pipelines instead of the
  structured `Read`/`Edit`/`Grep` tools). Still worth a look since every `Bash` call
  round-trips through a full model turn and its raw stdout becomes context text that
  has to be re-parsed by the model, whereas e.g. `Read`/`Grep` results are already
  structured — but it's a general efficiency lever, not something specific to what
  Kairos's commands themselves instruct.

## Finding 2 — where the tokens actually go

- **Prompt caching is healthy everywhere** (97.6-98.3% hit rate). This rules out
  "broken caching" as a driver of cost — don't spend time chasing that.
- **Extended thinking is the single biggest lever visible in this data.** In both
  opus/xhigh/thinking Kairos runs, thinking tokens are **~45-49% of all output
  tokens** — output_tokens_total was 565,176 for the epic run and 457,111 for the
  wave run, so roughly a quarter-million tokens *each* went to invisible reasoning,
  vs. 0% in the (thinking-disabled) `create-story` run and 25.5% in the mixed-effort
  baseline. Thinking tokens are billed as output tokens. Whether that's worth it
  depends entirely on where it's spent: a Bash-heavy mechanical step (running a
  command, reading its output, running the next command) plausibly doesn't need the
  same reasoning depth as, say, deciding an architecture. `calls.csv` has
  `thinking_tokens` per call and `tool_names` for what it was doing — worth grouping
  by tool/phase to see if thinking is concentrated in genuinely hard steps or spread
  evenly across rote ones (in which case a lower effort for those phases is free
  savings).
- Every call in the Kairos archives re-sends **19 tool schemas** and the full system
  prompt; at 97-98% cache hit rate this is mostly free on the input side, but note
  `system_chars` and `n_tools_declared` per call in `calls.csv` if you want to check
  whether that's stable across the run or grows (e.g. after `ToolSearch` calls
  register more deferred tools into context).
- Total billed input tokens: create-story 4.5M, epic 170.8M, wave 147.4M, baseline
  27.6M. The Kairos runs are ~6-30x the baseline's per-token spend, but they're also
  doing categorically more work (a whole epic/wave vs. one PRD → stories step) — a
  fair comparison needs a per-story or per-unit-of-work normalization that this data
  doesn't give you directly (story count is in the archive name, not the calls).

## Finding 3 — the review "context bug", root-caused and priced

Both Kairos archives hit the **same root cause**, independently, in two different
stories, each time forcing a manual multi-step workaround. This is the strongest,
most actionable finding in this dataset.

**Root cause:** the `security-review` / `code-review` skills derive "the diff under
review" from **committed** history (a branch/commit range). Kairos's epic-shared-worktree
model (see the project's own `CLAUDE.md`) deliberately does **not** commit during
implementation — work stays as unstaged changes, and each story only gets committed
at `close-story`. So a review launched mid-story, before that commit exists, has
nothing correct to diff against. This showed up two ways:

1. **Epic archive, STORY-119** (mtime window 1787938151-1787938249, session
   `3dd63419-90b1-4d26-a253-e54770f25339`): `security-review` returns an empty diff
   twice in a row ("DIFF CONTENT is still empty: everything is staged with zero
   commits"). The agent tries `git add -N` to force a working-tree diff — still
   empty, because the skill's preamble reads from commits, not the working tree. It
   ends up **committing the story's changes early**, specifically to satisfy the
   review tool, before re-running it successfully. Separately, in the same window, the
   agent discovers via `ToolSearch` that its own session was never `EnterWorktree`'d
   into the shared epic worktree in the first place, and has to fix that too.
   **Cost: 3 `security-review` invocations in 68s, ~940K billed tokens across the
   6-call cluster** (`incidents_repeated_skill.csv`, row 1); the full detour from
   first realizing something was wrong to the review actually running for real
   (1787938091 → 1787938314, 223s) cost ~2.9M billed tokens and 24 calls — though
   that wider window also includes legitimate review work, not pure waste.
2. **Wave archive, STORY-126** (mtime window 1787940351-1787940404, session
   `a6ed9e68-693c-432a-926d-ed429c5bd88d`): same root cause, different symptom — the
   review harness computes the diff as `origin/main..HEAD`, which is **the previous
   story's (STORY-105's) already-committed backend changes**, not this story's
   pending frontend changes. Caught by the agent itself mid-run: *"The security-review
   harness computed the diff from origin/main..HEAD — that is STORY-105's backend
   commits, not my pending frontend changes."* It works around this by manually
   building a diff file (`git add -N` + `git diff` piped to a scratch file) and
   handing that file directly to a hand-spawned subagent, bypassing the review skill's
   own diff-detection entirely. **Cost: 53s, 14 calls, ~2.85M billed tokens, 8235
   output tokens** for this one detour alone.

Two occurrences, two different failure shapes (empty diff vs. wrong-branch diff), one
shared cause: **the review skills' diff detection assumes a commit-based workflow, and
Kairos's own primary execution model (epic-shared worktree, commit-at-close) doesn't
provide one until the story is done.** The recommendation space is narrow and fairly
concrete — e.g. have the review skill accept/detect a working-tree diff (`git diff` /
`git diff --staged`, no `add -N` gymnastics needed) as a first-class input when no
usable commit range exists, or have `implement-story`/`implement-epic` pass the diff
scope explicitly instead of letting the review skill infer it. This is worth
weighing against the `CLAUDE.md` guardrail of "no commits during implementation" —
whatever the fix is, it shouldn't quietly encourage early commits as a workaround,
since that's what happened here and it's exactly the pattern the worktree model was
designed to avoid.

`incidents_repeated_skill.csv` is a generic detector (same skill name invoked ≥2×
within 180s in the same session) — it caught both of the above but would also catch
any other retry-shaped pattern in future captures, so it's worth re-running after any
fix to confirm the incidents disappear.

## Suggested next passes for the deep-dive model

1. Read the raw text/thinking around the biggest non-tool-turn gaps (Finding 1) to
   settle how much of that ~8000s/archive is genuine human/approval wait vs. avoidable
   idle time — this data narrows it down but can't answer it directly.
2. Group `calls.csv` by `tool_names` (or `skill_calls`/`agent_calls`) and sum
   `thinking_tokens` / `billed_input_tokens` per group, to check whether extended
   thinking is concentrated on hard steps or spread evenly (Finding 2) — if spread
   evenly, a lower default effort for mechanical phases (plain `Bash`/`Edit` turns)
   is close to free savings.
3. Design the actual fix for Finding 3 against the two concrete failure traces above,
   then re-run this script on a fresh capture to verify `incidents_repeated_skill.csv`
   comes back empty for review-related skills.
4. `chains.csv` has per-subagent-spawn cost; worth checking whether any single
   subagent chain (e.g. a `Task`-spawned reviewer) is disproportionately expensive
   relative to what it accomplishes.

## Caveats

- Four archives, one project, one user, one time period — this is enough to find
  concrete bugs (Finding 3) and directional signal (Findings 1-2), not enough to
  claim statistically robust baselines.
- Zip-stored timestamps have 2-second resolution (DOS timestamp format) — fine for
  the minute-scale analysis above, not for sub-second timing.
- `latency_s` is an approximation (see column notes above); `gap_before_s`,
  `turn_index`, `chain_root`, and all token/usage figures are exact, sourced directly
  from each response's `usage` block.
- `session1_nokairos` bundles 7 distinct conversations under one archive; its
  aggregate row in `archive_summary.csv` is a blend of all 7, not one continuous run.
